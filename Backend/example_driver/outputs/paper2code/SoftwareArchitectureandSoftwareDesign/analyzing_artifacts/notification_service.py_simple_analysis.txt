### **Purpose and Role**

The `NotificationService` class is responsible for handling notifications within the event-driven order processing system. It achieves decoupling by subscribing to specific events via the `EventBus`, such as `'PaymentProcessed'`, and upon receiving relevant events, it sends notifications (mocked as print statements). Its design emphasizes adherence to key software principles:

- **Single Responsibility Principle (SRP):** Dedicated solely to notification handling.
- **Open-Closed Principle (OCP):** Extensible to support additional events without modifying existing code.
- **Interface Segregation Principle (ISP):** Implements only the necessary event handling interface.
- **Dependency Inversion Principle (DIP):** Depends on abstractions, specifically `EventBus`, enabling loose coupling.

### **Key Components & Data Structures**

- **Attributes:**
  - `event_bus`: An instance of `EventBus`, injected during initialization, providing the `subscribe()` method.
  
- **Methods:**
  - `__init__(self, event_bus: EventBus)`: Stores the `event_bus` instance; sets up initial subscription.
  - `on_event(self, event_type: str, payload: dict)`: Handles events matching its subscription criteria; performs notification actions.
  - `subscribe_events(self)`: Registers `on_event` as a callback for relevant event types, specifically `'PaymentProcessed'`.

### **Subscription and Event Handling Workflow**

1. **Initialization (`__init__` method):**
    - Store the provided `EventBus` instance.
    - Call `subscribe_events()` to register event handlers.
    
2. **Event Subscription (`subscribe_events` method):**
    - Invokes `event_bus.subscribe()` for each relevant event type, e.g., `'PaymentProcessed'`.
    - Usually, the subscription involves passing the callback `self.on_event` and buffering which event types to listen to.
    - The subscription mechanism internally will call `on_event()` whenever a matching event occurs.

3. **Event Reception and Processing (`on_event` method):**
    - Receives `event_type` and `payload`.
    - Checks if `event_type` equals `'PaymentProcessed'`.
    - If so, extracts necessary data from `payload`:
        - `order_id`: ID of the associated order.
        - `status`: Payment status/result.
    - Simulates sending a notification:
        - Prints/logs a message such as: `"Notification: Payment for order {order_id} completed with status {status}."`
  
4. **Additional Event Handling:**
    - If extended to support more events, `on_event` can be extended with conditional logic or a dispatch table to handle other event types.
    - As per current scope, focus solely on `'PaymentProcessed'`.
