# Logic Analysis for utils.py

The `utils.py` module serves as a collection of utility functions supporting the entire pipeline of PDDL generation, refinement, execution, and evaluation. Its main purpose is to enable modular, reliable, and reproducible operations across various parts of the system—such as file handling, subprocess management, environment interaction, and metrics calculation—while maintaining consistency with the methodology described in the paper.

Below is a detailed, structured breakdown of the core functionalities required in `utils.py`, aligned with the paper’s approach, configuration parameters, and the overall experimental framework.

---

## Core Functional Responsibilities

### 1. File Handling and I/O Utilities

- **save_pddl_files(domain_code: str, problem_code: str, out_dir: str) → None**
  - *Purpose:* Save generated domain and problem PDDL code snippets into respective files (`domain.pddl`, `problem.pddl`) within the specified directory.
  - *Details:* Use `os.path.join()` to construct file paths; open files in write mode; handle encoding.
  - *Alignment:* Ensures the output files are correctly written for planner execution and environment validation.

- **load_pddl_files(domain_path: str, problem_path: str) → Tuple[str, str]**
  - *Purpose:* Load previously saved PDDL files for validation, domain refinement, or plan execution.
  - *Details:* Read files; handle file not found errors; return raw strings for parsing and validation.

- **load_json_or_yaml(file_path: str) → dict**
  - *Purpose:* Load configuration files or dataset annotations in JSON or YAML as needed.
  - *Details:* Use `json` and `yaml` modules.

### 2. Subprocess and External Tool Invocation

- **run_external_planner(domain_file: str, problem_file: str) → list**
  - *Purpose:* Call the classical planner (e.g., FastDownward) with specified domain and problem files.
  - *Details:* Use `subprocess.run()` with appropriate command-line invocation based on `config.yaml` paths; capture stdout/stderr; parse planner output to extract plan steps.
  - *Return:* List of actions (as strings) if a plan is found; empty list or exception otherwise.
  - *Alignment:* Enables the core plan generation step, as shown for evaluation in the paper.

- **plan_exists(domain_file: str, problem_file: str) → bool**
  - *Purpose:* Check for plan existence without parsing full output.
  - *Details:* Use `run_external_planner()` and check for a valid plan in the result.

### 3. Environment Interaction & Simulation

- **execute_action(env_api: dict, environment: Environment, action: str) → bool**
  - *Purpose:* Execute a given action in the environment via its API.
  - *Details:* Send action command (API call); process response; return True if execution succeeds.
  - *Alignment:* Critical during exploration walks, environment simulation, and validation of sampled sequences.

- **check_executability(env_api: dict, environment: Environment, action_sequence: list) → bool**
  - *Purpose:* Test whether a sequence of actions is feasible within the environment.
  - *Details:* Iteratively call `execute_action` if environment supports step execution, or simulate feasibility via an API function.
  - *Note:* Some environments may allow only partial checking; in such cases, simulate or invoke a validation API.

- **validate_plan(env_api: dict, environment: Environment, plan: list) → bool**
  - *Purpose:* Check whether a plan solves the environment problem based on `V_{d,p}`.
  - *Details:* Possibly re-execute the plan or use environment's validation function. Return boolean success.

- **get_object_list(environment: Environment) → list**
  - *Purpose:* Retrieve the list of environment objects (e.g., blocks, robots, targets).
  - *Details:* Call `environment.get_object_list()`.

- **get_action_interface(environment: Environment) → dict**
  - *Purpose:* Retrieve environment API details, e.g., valid actions and their parameters.
  - *Details:* Call `environment.get_action_interface()`.

### 4. Metrics and Statistical Calculations

- **compute_ew_score(environment: Environment, domain: str, problem: str, T_max: int) → float**
  - *Purpose:* Perform sampling of random action sequences using `check_executability()`, then compute the **EW** metric.
  - *Details:* 
    - Sample multiple random sequences of length `T_max`.
    - For each, determine if executable.
    - Calculate the fraction of sequences that are executable.
    - Possibly average over multiple runs/seedings.
  - *Alignment:* Serves as the domain similarity and refinement steering metric.

- **compute_metrics(success_list: list, ew_scores: list) → dict**
  - *Purpose:* Aggregate results such as overall solve rate, average EW score, and other statistics.
  - *Details:* Simple calculations with numpy/pandas.

### 5. Statistical & Random Sampling Helpers

- **sample_random_action_sequence(domain: str, problem: str, env: Environment, T_max: int) → list**
  - *Purpose:* Generate a random, executable sequence of actions in the environment, guided by available actions and the environment API.
  - *Details:* At each step, query `check_executability()` for available actions; randomly pick one; execute or simulate.

- **generate_random_candidates(current_pddl_files: dict, n_p: int, n_d: int) → list**
  - *Purpose:* Prepare multiple candidate PDDL files for domain or problem generation using GPT-4 prompts.
  - *Details:* Wrap GPT API calls with prompt templates, handle sampling, store responses.

## 6. Auxiliary Functions

- **log_message(message: str) → None**
  - *Purpose:* Standard logging with timestamps, verbose levels.
  - *Details:* Supports debugging and process tracking.

- **time_measurement(func: callable, *args) → Tuple[any, float]**
  - *Purpose:* Measure execution time of key functions (sampling, planning, environment interactions).
  - *Details:* Helpful for resource management and cost estimation.

- **calculate_costs(token_counts: dict) → dict**
  - *Purpose:* Keep track of prompt and response token counts, estimate LLM cost following experiment configurations.
  - *Details:* Use provided token counts in the paper for punctilious cost calculation.

## 7. Compatibility & Integration Considerations

- **Standardize interfaces:**
  - All functions should accept and return clearly defined data types (e.g., strings, bools, lists).
  - Use PDDL code as strings; environment objects and API details as dictionaries or class instances.

- **Error Handling:**
  - Robust try/except blocks for subprocess calls, file I/O, and API failures.
  - Return meaningful success/failure signals to guide the refinement process.

- **Config-driven parameters:**
  - Extract values such as `n_p`, `n_d`, `c_max`, `T_max`, `temperature_initial`, etc., from `config.yaml`.
  - Parameters should be passed explicitly for flexibility.

---

## 8. Examples of Function Implementations (High-level)

- `save_pddl_files()`: Write strings to designated `.pddl` files.
- `run_external_planner()`: Call the planner with subprocess, parse output for plan.
- `check_executability()`: Loop through actions; execute via environment API; if any fail, return False.
- `compute_ew_score()`: Sample multiple random sequences; check executability; average.

`utils.py` is the backbone of modularity, enabling core functions necessary for protocol adherence, including data/file management, environment interaction, sampling, plan execution, and metrics calculation—all aligned with the paper’s experimental methodology. Each function must be implemented with robust error handling and configurability to support the iterative refinement loop and evaluation benchmarks explicitly described.

This detailed logic analysis guides the subsequent development of precise, clean, and reliable utility functions to implement the research methodology faithfully.
